# M4 구현과 검증 기록

기준 커밋: b08f3ca. [작업](../tasks/M04-named-pipe-ipc.md), [IPC 계약](ipc-contract.md), [ADR-0011](adr/0011-named-pipe-protocol.md)과 [ADR-0012](adr/0012-start-request-replay.md)를 함께 읽는다.

## 구현

Core 계약을 그대로 사용하면서 Host가 DTO 변환과 Named Pipe 서버를 소유한다. Contracts는 DTO·버전·제한·오류 코드, Client는 요청 파일과 연결 왕복을 담당한다. StartJob/StartAuto의 응답은 실행 접수이며 결과 저장 완료는 상태 조회로 확인한다.

시작 응답을 연결에 쓰기 전에 Host에 보관한다. 연결이 끊겨도 검사 수명은 유지되며 같은 요청 재전송은 같은 RunId/AutoId를 반환한다. 자동 중지와 현재 취소를 분리한다. JSON 읽기는 실제 게시된 결과만 반환하며 저장 실패의 계산 결과는 상태 진단에 남긴다.

## 실제 검증

전체 verify `20260927T114515Z-15d2aeda`에서 Core 83 + 통합 63 = 146개가 통과했고 실패·skip은 0이다. 통합 중 실제 Native 34, 파일 6, IPC 23개를 확인했다. IPC는 Host 프로세스 21개 사례와 Client 응답 검증 2개이며 Host 사례 중 4개는 별도 Client 실행 파일로 시작한다. 기존 CLI 단일·자동 JSON과 저장 오류·타임아웃·DLL 누락 검증도 유지했다. 94개 검증 항목의 정확한 146개 사례, ADR 12건·그림 9개·링크를 검사했다. 소스/DLL 해시와 최종 문서 재검증 절차는 작업 기록에 있다.

개발 중 콘솔 입력 대기, Pipe 버퍼 흐름, 손상 연결 격리와 재사용 문제를 실제 테스트 및 자체 리뷰로 수정했다. GetStatus 단계·상태와 준비 출력을 기다렸으며 임의의 경과 시간으로 동시성 성공을 판정하지 않았다. 별도 리뷰 호출은 하지 않았다.

## 직접 확인할 학습 항목

- RequestId와 RunId의 차이 및 시작 응답 유실 시 재시도 ID를 설명한다.
- Accepted와 Succeeded의 차이, 저장 실패 시 ComputedResult의 의미를 설명한다.
- Pipe 연결 종료가 검사 취소가 되지 않는 이유를 설명한다.
- Busy 응답을 재전송할 때와 새 시도를 할 때의 ID 선택을 설명한다.
- StopAuto와 CancelRun을 조합하고 상태·결과 파일을 비교한다.
- 재시작 이후 중복 방지를 보장하려면 어떤 영속 기록이 더 필요한지 판단한다.

구현·검증은 Codex가 수행했으며 사용자의 직접 설명·수정·재현은 아직 확인하지 않았다. 다음 구현 단계는 M5다.
