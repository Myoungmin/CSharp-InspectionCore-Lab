검토일: 2026-09-29. 기준 구현: `45792b8`. 아래는 검토 당시 상태이며, 이후 B04 구현·원격 검증 상태는 [DEV03](../tasks/DEV03-windows-ci.md)과 [현재 CI](continuous-integration.md)에 기록한다. [검토 작업과 증거](../tasks/DEV02-architecture-review.md), [현재 아키텍처](architecture.md), [후속 목록](backlog.md)을 함께 읽는다. 이 문서의 후속 구성은 제안이며 구현 완료나 새 아키텍처 결정의 채택을 의미하지 않는다. 착수할 때 작업별 ADR·인수 조건을 확정한다.

## 완료 범위와 현재 구조

M0~M6의 기능 구현·통합 검증은 완료했다. .NET 10 전환을 보류해도 해당 완료 상태는 유지된다. 자동 반복 제어기, 원격 CI, 장기 운영은 별도 미구현 범위이며 사용자의 직접 실습·학습 완료도 구분한다.

| 경계 | 확인한 구현 | 판단 |
| --- | --- | --- |
| Core | 외부 포트·모델, Runner의 네 단계, Engine의 접수·취소·자동 반복 | 책임 분리를 유지한다. 지금 범용 workflow나 추가 계층은 필요하지 않다. |
| Host | 검사기·저장소·진단 생성, IPC 변환, 서버→Engine→어댑터→로그 종료 | 조립과 수명을 한곳에서 판단할 수 있다. |
| Native/C++/CLI | 두 ABI 호출 방식, 동일한 관리 작업·콜백·SafeHandle 수명 | 비교 목적에 적합하다. 독립적인 C++/CLI 수명 구현·성능 비교까지 완료한 것은 아니다. |
| IPC | Contracts DTO, Client의 Core 참조 없음, Host의 접수 재전송 | 프로세스 경계가 유지된다. 재시작 후 같은 RequestId의 중복 방지는 보장하지 않는다. |
| 저장·진단 | commit 후 성공, 실행과 독립된 조회, 잠금 밖 최종 진단 | 기본 계약이 연결돼 있다. 로그·DB의 보존·복원은 추가 범위다. |
| 개발 구조 | 작업 기록, ADR 16건, 그림 11개, 필수 사례 217개와 소스 해시 | 기능 확장의 기반은 마련됐다. 원격 반복 검증과 보호된 자동 제어기는 아직 없다. |

검토한 참조·소유권·완료 경계에서 현재 기능을 막는 구조적 변경 필요성은 확인하지 못했다. 모든 코드 경로의 무결점이나 실제 장비·장시간 운영 적합성을 인증한 검토는 아니다. 로드맵에서 빠진 C++/CLI 프로젝트·네 그림, 오래된 서버 종료 설명과 이전 우선순위는 이번 문서 변경으로 정리했다.

## 권장 진행 순서

학습·개발을 이어가는 현재 목적에서는 **CI 최소 구성(B04) → 로컬 Codex 반복 제어기(B03) → 장기 운영(B08)**을 권장한다. CI는 사람이 만든 변경과 AI가 만든 변경에 같은 검증을 제공한다. 원격 CI 준비가 늦어져도 B03의 보호된 검증 실행기는 로컬에서 먼저 만들 수 있다. 실제 장시간 운영을 시작할 계획이면 B08의 보존·백업·복원 검증을 먼저 수행한다. .NET 10 전환(B01)은 이 순서의 선행 조건이 아니다.

## B04 — CI와 증거 보관

현재 저장소에는 GitHub Actions workflow가 없으며 `scripts/verify.ps1`은 로컬에서 실행한다. 최소 CI는 새 checkout에서 같은 명령을 실행하고 실패 원인을 다운로드할 수 있게 만드는 것으로 충분하다. 자동 수정·병합·배포는 첫 CI 범위에 넣지 않는다.

GitHub Actions를 선택한다면 `windows-2022`를 후보로 사전 검증한다. 공식 이미지 목록에는 C++/CLI 구성 요소가 있지만, 그것만으로 프로젝트가 요구하는 정확한 MSVC `14.44.35207`의 존재를 증명하지는 못한다. 확인한 SDK 목록도 `9.0.305`와 다르므로 고정 SDK 설치가 필요하다. 원격 실행 가능 여부는 실제 runner의 도구 검사와 빌드로 판단한다. [GitHub 공식 Windows 2022 이미지 목록](https://github.com/actions/runner-images/blob/main/images/windows/Windows2022-Readme.md)

최소 작업 구성 제안:

1. PR·주요 브랜치 변경·수동 실행에서 Windows x64 checkout을 준비한다. SDK 9.0.305, 고정 MSVC/Windows SDK, C++/CLI, Java와 해시가 일치하는 PlantUML JAR를 검사한다. 도구가 없으면 환경 실패로 보고하고 Native 사례를 skip하지 않는다.
2. `powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/verify.ps1`을 한 진입점으로 사용한다. 최초 checkout의 빌드·패키지 복원 제한 시간은 실제 cold-run 측정 후 별도 작업에서 정하며 테스트 자체의 hang 제한과 구분한다.
3. 성공·실패 양쪽에서 summary.json, TRX, stdout/stderr, source-manifest.json, IPC 프로세스 로그와 도구 버전을 artifact로 보관한다. 검증이 요약 파일 생성 전에 실패한 경우도 환경 로그를 남긴다. 보관 기간은 예를 들어 14일로 시작하되 사용 목적·용량에 맞춰 결정한다.
4. 초기에는 DLL/bin/obj 캐시 없이 재현성을 확인한다. 이후 캐시는 NuGet 잠금 파일과 도구 버전으로 구분한다. 플랫폼·컴파일러 차이로 생긴 실패를 캐시나 테스트 제외로 숨기지 않는다.
5. 정확한 도구를 hosted runner에 확보할 수 없으면 고정 이미지의 일회성 Windows runner를 대안으로 검토한다. 개인 개발 PC를 외부 PR의 코드 실행 runner로 사용하지 않는다. CI 계정의 기본 권한은 저장소 읽기로 제한하고 Codex 인증은 이 검증 job에 넣지 않는다.

완료 조건: 새 checkout에서 217개 필수 사례·Native/IPC/publish·문서 검증이 통과하고, 의도적으로 실패시킨 별도 후보에서 원격 job 실패와 증거 보관을 확인한다. 완료 후에 필수 상태 검사로 설정한다. 현재는 원격 runner 실행이나 저장소 정책 변경을 수행하지 않았다.

## B03 — Codex 자동 반복 제어기

설치된 CLI는 `codex-cli 0.155.0-alpha.16.3`이다. `codex exec --help`에서 `--sandbox`, `--json`, `--output-schema`, `--output-last-message`를 확인했다. 공식 문서도 비대화형 호출·JSONL 이벤트·최종 JSON Schema 출력을 설명한다. 이 확인은 실제 인증·모델 호출·Windows 권한 격리의 종단 검증과 구분한다. [OpenAI 공식 비대화형 실행 문서](https://learn.chatgpt.com/docs/non-interactive-mode)

현재 verify는 검증 시작·종료 사이의 소스 변경과 TRX 누락을 검사한다. 그러나 **후보 변경이 실행 전에 verify·필수 테스트·대응표 자체를 수정하는 경우까지 차단하는 제어기는 없다.** B03의 첫 작업은 반복 횟수 루프보다 이 기준 분리다.

최소 구조는 저장소 밖 제어 실행 영역, 후보 worktree, 쓰기에서 보호된 기준 검증 묶음의 세 부분으로 제안한다. 보호 대상에는 verify와 process/build/check 스크립트, 필수 테스트·대응표, 도구·인수 조건을 포함한다. 현재 검증 스크립트는 PSScriptRoot로 저장소를 찾으므로 단순 파일 복사만으로 분리됐다고 주장할 수 없다. 후보 루트를 명시적으로 받아 보호된 기준과 후보 소스를 함께 검사하는 실행기를 먼저 설계·검증한다. 프로세스 권한으로 보호하고 실행 전후 해시도 확인한다.

한 작업의 진행 순서 제안:

1. taskId, 기준 commit, 허용 경로, 고정 인수 조건과 CLI·모델 설정을 기록한다. 시간 제한을 비용 상한으로 간주하지 않고 사용량·예산 정책을 별도로 정한다. 사용자 미커밋 변경과 분리한 worktree를 만들고 한 작성자만 사용한다.
2. 작성 호출은 필요한 workspace 쓰기만 허용한다. 명령 프롬프트·환경·인증 주입 범위를 고정한다. CLI 제한 시간 초과 시 자식 프로세스까지 정리하고 원본 작업 트리·프로세스에는 영향을 주지 않는다.
3. 제어기가 보호된 검증을 직접 실행한다. 종료 코드, 정확한 TRX 사례, 결과 파일과 소스 해시를 확인한다. 후보가 기준을 변경하면 해당 시도를 중단하고 별도 사람 검토 작업으로 돌린다.
4. 통과한 후보를 새 `codex exec --sandbox read-only` 호출로 검토한다. 신규·수정·삭제 파일 전체와 계약·검증 증거를 제공한다. JSON Schema에 맞는 응답만 받고 실제 후보 해시는 제어기가 계산한다. 쓰기 차단과 리뷰 전후 해시 일치를 함께 확인한다.
5. 지적 수정 후 전체 검증과 리뷰를 다시 수행한다. 최초 구현 포함 최대 3회, 검증·리뷰를 포함한 총 30분, 동일 실패 2회 연속 중지라는 원래 제한을 유지한다. 같은 실패는 단계·오류 코드·정규화한 원인으로 비교하고 시각·RunId 차이는 제외한다.
6. API/환경/권한 실패, 시간·횟수 초과, 검증 실패, 검토 지적, 통과를 구분해 보고한다. JSON 손상·결과 누락·중단된 프로세스를 통과로 취급하지 않는다. patch·신규 파일 내용·검증·리뷰·최종 해시를 남기고 자동 main 병합은 하지 않는다.

제어기는 먼저 가짜 CLI와 작은 fixture로 성공, 기준 변경, skip, 손상 JSON, hang, 반복 한도, 신규 파일 누락을 검증한다. 이후 승인된 작은 실제 작업 한 건으로 작성→검증→새 리뷰를 실행한다. CLI 버전 변경 때도 이 계약을 재확인한다. 이 문서는 해당 제어기나 실제 Codex 호출을 실행한 기록이 아니다.

## B08 — 장기 운영

현재의 결과 재조회는 구현됐지만 결과·로그 보관 기간, 회전, 백업·복원, 스키마 이전, 프로세스 재시작 정책은 미구현이다. 자동 실행을 오래 켜 두기 전에 아래 항목을 작은 작업으로 나누는 편이 적절하다.

| 세부 작업 | 현재 근거와 추가할 최소 범위 | 완료 증거 |
| --- | --- | --- |
| B08a 로그·디스크 | JsonDiagnosticLog는 동기 WriteLine/AutoFlush이며 실패 후 기록을 중지한다. 날짜/크기 회전·보존 범위·여유 공간·기록 장애 상태를 추가한다. | 회전 경계에서도 Sequence/ID 추적, 쓰기 거부·용량 부족 재현, 활성 파일 보존 |
| B08b 백업·복원 | SQLite WAL 사용 중 DB 파일만 복사하지 않는다. 별도 백업 파일을 만들고 검증 후 게시하며 복원은 Host가 정지한 상태에서 수행한다. | 백업 시점 행 조회·무결성, 새 위치 복원, 실패 시 기존 DB 보존 |
| B08c 유지·이전 | 결과 보존 기간, 삭제 범위, 버전별 migration과 실패 rollback을 정의한다. 보존 삭제는 기본 비활성으로 시작한다. | 미승인 파일/결과 보존, 오래된 스키마 변환, 실패 복구·알 수 없는 버전 거절 |
| B08d 상태·복구 | Host의 로그 건강도·디스크·시작 재전송 용량을 노출하고 종료 제한·재시작 절차를 정한다. | 조회/취소 응답, 재접수 차단, 재시작 후 결과 복원과 실행 미복원 구분 |

SQLite 온라인 백업에는 Microsoft.Data.Sqlite의 `SqliteConnection.BackupDatabase`를 사용할 수 있다. 공식 문서는 백업 동안 다른 연결의 쓰기가 막힐 수 있음을 설명하므로, 처음에는 자동 예약 중지와 현재 실행 완료를 확인한 유지보수 시점에 백업하는 방식을 후보로 둔다. [Microsoft 공식 온라인 백업 문서](https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/backup)

로그 **예외 격리**는 느린 I/O의 **비차단**을 뜻하지 않는다. 현재 최종 진단이 반환되기까지 Engine 완료·Dispose가 대기하고 일부 IPC 진단도 동기 기록한다. 비동기 로그 큐를 도입한다면 큐 상한·포화 시 정책·종료 drain·어느 시점을 기록 완료로 볼지 먼저 결정해야 한다. ADR-0014를 대체하거나 확장하는 ADR 없이 완료 경계를 바꾸지 않는다.

시작 재전송 기록은 Host 수명 동안 최대 4,096개다. 한 자동 세션의 반복 4,096회 제한이 아니라 서로 다른 시작 요청 ID의 보존 한도다. 단순 캐시 삭제는 동일 요청의 재실행을 허용하므로 TTL/삭제를 넣으려면 IPC 계약을 다시 결정한다. 지금은 조회·취소를 유지하고 새 시작을 거절하는 기존 동작을 운영 상태에 보여 주는 것이 우선이다.

Wait 미확인 시 자원 보존과 Engine Faulted를 유지한다. 감시자가 프로세스를 재시작하더라도 진행 중 검사·자동 예약·RequestId 복구가 구현되는 것은 아니다. 영속 접수·재시작 실행 복구는 결과 백업과 다른 별도 계약이다. 실제 Native SDK가 협조적 종료를 보장하지 않는다면 worker 프로세스 격리는 그 SDK 연동 작업에서 검토한다.

장시간 검증은 무작정 지연하는 테스트 대신 반복 수·관찰 상태·실행 제한을 정하고 정상 반복의 핸들/메모리 증가, 결과 수, 로그 회전, 재시작 조회를 확인한다. 현재 217개 테스트는 이 장기 운영 검증을 대신하지 않는다.

## 이번 검토의 결과

현재 제품 구조는 유지하고 위 세 작업을 별도 범위로 진행할 수 있다. B03/B04는 개발 도구에 두며 Core가 Codex나 CI를 참조하지 않는다. B08도 우선 Host 진단과 Infrastructure 저장 구현에 배치하고, 운영 요구 때문에 공개 계약이 바뀔 때만 Core/Contracts와 ADR을 함께 변경한다. 공급자 선택·실제 제어 호출·원격 CI·보존 삭제·백업은 이번 검토에서 실행하지 않았다.
