# M03a — 단일 실행 접수와 상태·취소·타임아웃

상태: Verified. 기준 커밋: 7e4f269. M2와 DEV01 검증·커밋 이후 착수했다.

## 목표와 범위

InspectionEngine이 실행 자리 하나를 접수하고 Busy·상태 조회·RunId 대상 취소·시간 제한을 제공한다. Runner는 검사 한 건의 순서를 유지한다. Host는 Engine을 거쳐 managed/native를 실행하고 시간 제한 옵션을 제공한다. Native Start/Stop/Wait·진행 콜백은 M3b, 자동 반복은 M3c, IPC는 M4다.

## 인수 조건

- 동시에 시작해도 한 요청만 Accepted이며 나머지는 Busy다. 거절된 요청은 장비를 호출하지 않는다.
- 접수 RunId와 실제 결과 RunId가 같다. 상태 스냅샷과 완료 Task를 제공한다.
- 취소·타임아웃 원인의 최초 접수와 Persisting 진입을 같은 잠금으로 판정한다.
- 취소 요청 후에도 실제 실행과 토큰 콜백이 종료될 때까지 Busy를 유지한다. 타임아웃이 Native 강제 중단을 뜻하지 않는다.
- 저장 전 먼저 접수된 취소는 저장을 막고, 저장 진입 이후 취소·시간 초과는 저장 결과를 바꾸지 않는다. 저장 실패의 계산 결과를 유지한다.
- 시간은 TimeProvider, 경쟁은 명시적 신호로 제어한다. 늦은 타이머가 다음 실행에 영향을 주지 않는다.
- 비동기 Dispose는 신규 접수를 막고 현재 실행·콜백 종료를 기다린다. 주입된 Runner·장비·검사기·저장소는 해제하지 않는다.
- 일반 실행 실패 후 재실행을 허용한다. 취소 콜백 실패는 엔진 Faulted로 기록하고 새 실행을 거절한다.
- 기존 M1/M2의 42개 필수 사례를 유지하고 Engine 사례·콘솔 타임아웃·상태 및 취소 그림을 추가한다.

## 아키텍처 결정

[ADR-0006](../docs/adr/0006-single-run-engine.md)은 단일 접수와 상태 보관 범위, [ADR-0007](../docs/adr/0007-stop-and-completion-arbitration.md)은 종료 원인·완료·수명을 정의한다. 기존 Runner 저장 경계의 동작은 유지한다.

## 검증 계획과 정책 변경

Engine 테스트 25개를 Core에 추가해 최소 수를 19개에서 44개로 늘린다. 기존 42개와 새 25개의 정확한 사례를 검증 대응표로 확인한다. 시간 경과는 수동 TimeProvider로 전진시키고 타이밍을 Thread.Sleep으로 추측하지 않는다. 정상·불량 Native와 파일 통합 23개 기준은 유지한다. 두 검사기의 즉시 Timeout(종료 124, 저장 없음)과 잘못된 시간 인수를 콘솔 검증에 추가한다. 새 상태·취소 다이어그램 두 개로 문서 필수 목록을 5개에서 7개로 확장한다. 변경은 M3a 인수 조건의 추가이며 기존 보장을 축소하지 않는다.

## 검증 증거와 리뷰

첫 전체 실행에서 67개 테스트는 모두 통과했으나 사례 대조는 MSTest 언어별 표시 공백 차이로 실패했다(`artifacts/verification/20260927T035622Z-92118985`). 초기 수동 실행의 `Method(args)`와 공통 검증의 `Method (args)`를 동일한 사례로 처리하도록 해당 구분 공백만 정규화했다. 클래스·메서드·인수 값은 계속 확인하고 대소문자를 구분한다. 필수 사례 누락 기준을 완화한 것이 아니며 두 TRX 표기와 이름·인수·대소문자를 바꾼 복사본을 따로 검증했다.

전체 verify.ps1은 `artifacts/verification/20260927T040034Z-7dcc7155/summary.json`에서 통과했다. Core 44개·통합 23개·필수 사례 67개, 두 검사기의 정상·불량·반복 6회와 즉시 Timeout 2회, 오류·배포 DLL·아키텍처·ADR 7건·다이어그램 7개를 확인했다. 메타데이터의 사례 중복 확인도 실제 TRX 대조와 같은 대소문자 구분을 적용했다. 최종 문서 정리 후 동일 명령을 다시 실행하고 해당 소스 해시·TRX는 별도 verification 폴더에 보관한다.

자체 리뷰에서 접수 슬롯의 잠금, 저장 경계, 최초 종료 원인, 실제 작업·콜백 대기, 늦은 타이머, Host 소유 자원의 해제 순서, Runner 기존 계약과 테스트 유지 여부를 확인했다. 상태·취소 그림은 실제 렌더링으로 검토했다. 별도 Codex 리뷰 호출을 실행한 것으로 기록하지 않는다.
