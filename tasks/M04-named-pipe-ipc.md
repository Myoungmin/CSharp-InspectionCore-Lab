# M04 — Named Pipe와 별도 Client

상태: Verified. 기준 커밋: `b08f3ca` (M3c). 마일스톤: M4. 구현 검증이며 사용자 학습 완료와 구분한다.

## 목표와 범위

별도 Client 프로세스에서 Host의 수동·자동 접수, 상태·결과 조회, 취소·예약 중지를 호출한다. 연결 수명과 실행 수명을 분리하고 시작 응답 유실을 RequestId로 복구한다. Contracts와 Client를 추가하며 Core의 실행·Native 수명 계약은 그대로 유지한다. SQLite, UI, 이벤트 push, 재시작 후 중복 방지와 Codex 반복 제어기는 이번 범위가 아니다.

## 인수 조건

- 별도 Host·Client 프로세스로 managed/native Pass/Fail을 실행하고 RunId별 실제 JSON을 조회한다.
- 재접속 뒤 실행 상태를 조회·취소한다. 시작 접수는 완료를 기다리지 않으며 다른 연결도 Busy·조회·취소 응답을 받는다.
- 같은 시작 RequestId의 동시 요청·응답 유실·완료 후 재전송은 기존 응답을 반환한다. 다른 내용은 충돌이다. 용량 한계에서도 기록을 퇴출하지 않고 조회·취소를 제공한다.
- StopAuto와 CancelRun을 구분하고 제품 Fail의 자동 반복, 타임아웃·저장 실패 진단을 유지한다.
- 부분·연속 프레임, 손상·잘린 입력, 버전·필드 오류를 격리한다. 잘못된 응답의 RequestId/버전은 Client가 거절한다.
- 서버 종료가 부분 프레임과 장비 대기 중에도 제한 시간 내 완료된다. Native 실제 종료 계약은 기존 필수 테스트로 계속 확인한다.
- 관련 필수 사례는 [검증 대응표](../docs/verification-map.md)의 M4 항목이다.

## 아키텍처 결정

[ADR-0011](../docs/adr/0011-named-pipe-protocol.md): DTO 경계, 프레임, 동일 사용자 통신과 연결별 오류 격리.
[ADR-0012](../docs/adr/0012-start-request-replay.md): 시작 접수의 재전송, 연결과 실행의 수명 분리, 조회 보존 범위.
Core의 기존 ADR-0009·0010은 유지한다. IResultStore 포트 변경 없이 구체 JSON 저장소에 읽기를 추가한다.

## 검증 계획과 정책 변경

기존 Core 83개·통합 37개를 유지하고 IPC 23개와 파일 읽기 3개를 추가한다. 총 146개(Core 83 + 통합 63)가 기준이다. 통합 중 21개는 실제 Host 프로세스, 그중 4개는 별도 Client 실행 파일까지 사용한다. 나머지 IPC 2개는 가짜 응답을 보내는 실제 Pipe 서버로 Client의 검증을 검사한다. Native 필수 34개는 별도로 계속 집계한다.

Host 준비 출력과 GetStatus의 실제 단계·상태를 관찰한 뒤 다음 행동을 한다. 취소 시험은 가상 장비의 취득 지연 60초를 설정하고 Acquire 관찰 후 취소하므로 지연 완료를 기다리지 않는다. 조회 사이 10ms는 폴링 간격이며 상태 도달을 가정하는 고정 대기가 아니다. fixture 전체 20초, 정상 종료 5초, Client 10초, testhost hang 30초 제한을 두고 실패 시 자식 프로세스를 종료한다. 로그는 artifacts/ipc-tests에 보존한다.

관리 프로젝트 검사를 6개에서 8개로 확장한다. Client는 Contracts만, Contracts는 BCL만 참조한다. IntegrationTests의 Host 참조는 빌드 순서용(`ReferenceOutputAssembly=false`)이며 실제 실행 파일은 별도 프로세스로 실행한다. Host/Client는 공유 transport 소스를 링크하고 Contracts에는 전송 구현을 넣지 않는다. 다이어그램은 8개를 유지하며 IPC 시퀀스를 추가해 9개다. 필수 사례는 후보 TRX에서 자동 재생성하지 않고 검토한 이름을 추가한다.

## 검증 증거와 리뷰

개발 중 전체 통합 테스트 62개 통과(실패·skip 0)를 확인했다. 초기 시험은 콘솔 동기 입력이 준비 출력을 막는 문제, 기본 Pipe 버퍼에서 연속 프레임 쓰기가 서로 대기하는 문제, InvalidDataException의 연결 격리 누락을 발견했다. 입력 읽기를 배경 작업으로 옮기고 취소 가능한 대기를 적용했으며, 명시적 입출력 버퍼와 오류 격리를 적용해 해당 사례가 통과했다.

자체 리뷰에서 broken Pipe도 Disconnect로 초기화해야 다음 연결을 받을 수 있음을 확인했다. 이를 수정하고 40회 부분 전송/즉시 단절 뒤에도 조회가 가능한 M4-020을 추가해 기준이 146개가 되었다. 접속 완료 전 단절로 손상된 인스턴스는 직렬로 교체하며 다른 listener는 유지한다. 손상 envelope는 신뢰할 RequestId가 없으므로 응답 없이 닫도록 확정했다. 가짜 ID 응답 후 즉시 Disconnect하면 아직 읽지 않은 버퍼가 소실될 수 있어 응답 도착을 보장할 수 없기 때문이다. 유효한 envelope의 payload 오류 응답 검증은 그대로 유지한다. 새 M4 계약을 구현 중 확정한 변경이며 기존 120개 필수 기준은 낮추지 않았다. 별도 리뷰 에이전트 호출은 하지 않았다.

전체 명령 `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/verify.ps1`이 `20260927T114515Z-15d2aeda`에서 Passed였다. 기준 커밋은 `b08f3ca23d6c16303856920dbd7d56da462af8c8`, 소스 SHA-256은 `13B5C18ACF3BEFCD6AB1C5E03A7EF9E2EB31190F5B4006EFE4DCA59F3B99045B`, DLL SHA-256은 `9742FEED4D483412AA11A2971B774048EDDB7D2380C13EDB8816B55C67C42832`다. Core 83개·통합 63개(실제 DLL 34, 파일 6, IPC 23)가 모두 실행되어 통과했고 실패·skip은 0이다. 기존 CLI 단일 6파일·자동 4세션 12파일·실패 시나리오, 정확한 필수 사례, ADR 12건·다이어그램 9개·링크 검사도 통과했다.

이 기록과 그림 시각 검토를 반영한 뒤 같은 전체 명령으로 최종 내용을 재검증한다. 해당 최종 source-manifest·summary·TRX는 artifacts/verification의 출력 ID와 커밋 보고에 연결한다. 자체 리뷰는 수명·접수 원자성·경계 크기·제한 용량·예외 격리·프로세스 정리·코드/ADR 일치를 확인했다. PNG로 세 그림을 확인해 오른쪽 라벨 잘림을 수정했고 참조 그림에는 Core 포트 책임 주석을 추가했다. 생성 SVG와 원본을 함께 커밋한다.

## 남은 일과 학습 확인

후속 M5는 SQLite 저장·검색과 구조화 진단이다. [보류 목록](../docs/backlog.md)의 B03 자동 제어기는 별도다. 구현·테스트는 Codex가 수행했으며 사용자 학습 완료를 주장하지 않는다. RequestId/RunId, 접수와 완료, 연결과 작업 수명의 구분을 [M4 실습](../docs/practice-M04.md)에서 확인한다.

## 완료 확인

- 인수 조건과 기존/신규 필수 검증의 통과 증거를 남겼다.
- ADR·현재 계약·그림·대응표를 갱신하고 소스와 실제 실행 증거를 연결했다.
- 사용자 학습 확인과 M5 이후 작업은 별도로 남겼다.
- 전체 설계 문서는 계속 추적하며 생성 SVG·잠금 파일·소스·작업 기록을 포함한다. artifacts의 결과·로그는 커밋하지 않는다.
